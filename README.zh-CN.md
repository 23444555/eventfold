# eventfold

**把一条条零散的事实，折成几段能塞进 prompt 的「经过」。**

向量召回给你的是碎片：十句话，每句都提到了那块硬盘。eventfold 给你的是整件事——
*「阵列最早用了 13.4 TB，后来第 5 块盘报临界，换盘重建 26 小时，现在 15.1 TB」*——一段有边界、
带日期的文本块。

一个零依赖的 ES 模块 + 一个纯标准库 Python 构建器。不调模型、不联网、不要数据库。
运行期只读一个文件：`archive.json`。

```js
import { archiveBlock } from 'eventfold';

process.env.MEMORY_ARCHIVE_JSON = './data/archive.json';   // 启动时指一次

const block = archiveBlock('备份阵列现在还剩多少容量？');
// -> "## 备份阵列（2026-02-11 ~ 2026-03-28，2 段）… 已用：13.4 TB … 已用：15.1 TB …"
```

十行，没有索引要建，没有服务要跑。把 `block` 放进对话模型的上下文，它就能回答 top-k
在结构上答不了的那种问题——"后来变成多少了"。

## 为什么需要这一层

长期记忆系统通常的做法是「存事实 + 按相似度取回」。这对「我显卡是什么型号」有效，对任何
**有过程**的问题失效：

- **top-k 是预算，不是摘要。** 同一件事在五天里被提了五次，五个名额就没了；而三周前只提过
  一次的那个原因，永远挤不进来。
- **问题经常问的是「变化」。** "最后是多少"需要第一个值和最后一个值同时在场。相似度没有
  「同一个字段、更晚的时间」这个概念——两句话对向量库来说是近似重复，它留一句丢一句，
  正好丢掉最该留的那半。
- **自由文本没有槽位。** 事实是散文进来的："已用 13.4 TB"、"现在用到 15.1 TB"。没有任何东西
  标记它们是同一个字段，所以没有人能做差。

eventfold 就是缺的那一层：一个**离线批处理**，把事实分组成「经过」、把自由槽位名折到一个
小词表上；加一个**运行期**，把问题路由到几段经过，渲染成有界、带日期的块。

它**不是**检索的替代品。请把它放在向量库**旁边**跑：向量负责"是哪一条"，经过负责"发生了什么"。

## 十分钟上手

需要 Node 18+ 和 Python 3.9+（只构建器用）。不用装任何东西。

```bash
npm test                                                 # 58 项检查，两套都跑
python build/archive_build.py \
  --facts examples/facts.jsonl \
  --out   examples/data/archive.json                     # 33 条事实 -> 19 段经过
node -e "process.env.MEMORY_ARCHIVE_JSON='examples/data/archive.json';import('./src/archive.mjs').then(m=>console.log(m.archiveBlock('备份阵列还剩多少容量？')))"
```

换成自己的事实，一行一个 JSON：

```json
{"id": 1, "ts": "2026-03-02 08:15", "thread": "运维", "schema": "incident-online",
 "subject": "反向代理", "text": "反向代理开始间歇性返回 502。",
 "slots": [{"n": "现象", "v": "502"}]}
```

`text` 和 `ts` 必填；`thread` / `schema` / `subject` / `slots` / `closed` 可选，缺了走启发式。
然后：

```bash
python build/archive_build.py --facts facts.jsonl --out data/archive.json \
  --mapping examples/mapping.json          # 可选：把槽位名折到词表上
node test/runtime_test.mjs                 # 体检一下产出
```

## 构建器对事实做了什么

四道确定性工序，不调 LLM：

1. **分组** —— 同一个 `schema`、同一个主体、间隔不超过 `--guard-days`、没被标记 `closed`、
   条数不超过 `--max-facts` 的事实，按时间顺序归为一段。
2. **折叠** —— 一千条事实会冒出两百种槽位名（`现象`、`症状`、`报错`）。闭合词表 + 别名 +
   bigram 相似度（≥ 0.34）把它们折到少数几个；仍然落不进去的**不丢、也不新造 key**，统一压进
   一个 `备注` 槽。
3. **劈开** —— 一个叫「其他」的线程攒到 300 条时，永远只能显示开头几条。构建器按日期断层把
   它劈成几段，每段又回到「一个人一口气能讲完」的粒度。
4. **落盘** —— 一个 `archive.json`：每段带 `title`、`status`、`first`/`last`、`summary`、
   `slots[]`、`facts[]`。

运行期再按「主体优先、相似度补齐」排名，扩到时间上的邻居段与同 schema 的兄弟段，最多铺 N 段 ×
M 条事实，**每一条都带日期**——"13.4 TB (2026-02-11)" 和 "15.1 TB (2026-03-28)" 并排出现，
模型不需要被叮嘱就会做对比。

## 运行期 API

| 导出 | 作用 |
|---|---|
| `archiveBlock(query, opts)` | 要放进 prompt 的那块；没命中返回 `''` |
| `flatFacts(query, k)` | 只给命中的事实行，不带段落框架 |
| `routeEvents(query, n)` | 带分数的经过列表，想自己渲染时用 |
| `routeStory(query, n)` | 沿同一个线程按时间排开的几段 |
| `routeSubjects(query, a, b)` | 按主体取段，而不是按相似度 |
| `complexity(query)` | 0/1/2 分级，多问句时用来放大预算 |
| `stats()` | 当前 archive 的 `{events, facts, threads, ...}` |
| `lastUsedEvents()` | 上一次 `archiveBlock` 实际用了哪几段 |

`archiveBlock` 的选项：`{limit, events, perEvent, threads}`，默认 `40 / 5 / 10 / 0`。

## 状态：什么被证明了，什么没有

请先读这一段再信数字。

- **它还没在真实对话数据上跑过。** [docs/EVALUATION.md](docs/EVALUATION.md) 里的评测用的是一份
  **合成语料**（一个虚构的自建机房爱好者：1,067 条事实 → 58 段经过）。这是可复现的基准，
  不是实测战绩。
- 在这份语料上跑了 **112 个提问实例**（44 个原话问 + 68 个改写问，改写会把人名和领域词抽掉），
  **12 个臂**、每问同一字数预算，全表见 [docs/EVALUATION.md](docs/EVALUATION.md)。
- 档案层总体 **56.2%** 铺齐全：**原话问 90.9%**（同预算纯事实召回 75.0%，配对 p = 0.035），
  但**改写问只剩 33.8%**。纯向量臂（bge-m3）总体 **73.2%**、改写问 63.2%，**显著强于档案层**
  （30 胜 11 负，p = 0.004）；跟 BM25 比总体是**打平**（55.4% vs 56.2%，p = 1.0）。
- 档案层 + 向量臂一起塞进去是 **83.9%**，但对得起的关键对照——向量臂填到**同样的字数**——是
  **80.4%**，差 **不显著**（8 胜 4 负，p = 0.39）。所以那点提升主要来自「上下文更多」，
  不是「结构检索得更好」；并集只是**单位分数更省**（5,068 字 vs 6,055 字）。
- **压到固定字数上限后，结构不值它花的字**：上限 1,200 / 2,400 / 4,800 字各跑一遍，纯向量
  赢或打平所有「留一部分预算给结构」的臂（最好的 `sib25`：57.1 / 70.5 / 80.4% vs 58.0 / 69.6 /
  79.5%，p 全 ≥ 0.5）。让档案块当检索器则每个上限都显著更差（1.2k 时 38.4% vs 58.0%，
  4.8k 时 66.1% vs 79.5%，p = 0.011）。结构唯一买到的是**原话问的多腿题**（4.8k 时 43/44 =
  97.7% vs 90.9%），改写问上又还回去。
- 一句话结论：**这个层没有比向量索引更能召回，它的优势是词面的**——问句复用了入库时的措辞时，
  它能在同样大小的块里铺得更好；换了措辞就塌。用向量当路由种子（`episodeSeed`：63.4%，
  改写问的塌陷从 57 点收窄到 27 点）是修法的形状，但还不到能默认上线的程度。
- 所以推荐的分工是：**向量负责挑事实，档案层负责排版**（日期、槽位、按事分段），不要用它挑候选。
- 判分是机械的（块里有没有答对所需的全部事实），量的是**证据召回**而不是答案质量，
  用 `node bench/ab-gen.mjs` + `python bench/ab-arms.py` + `python bench/ab-cap.py` 可复现。
- 诚实的定位：这是一个**参考实现**。机制是清楚的、有测试的；在你的数据上能不能赢，要你自己量。
- 构建器目前吃 JSONL 事实流，不直接对接任何记忆后端——这是故意的，也是你唯一必须自己写的那部分。
